# ТЗ: Java Blueprints — визуальная среда программирования

## 1. Цель

Веб-инструмент, который загружает Java-проект (монолит ~1000 строк), показывает его как код и как граф нод, находит проблемы производительности и качества, позволяет править программу в нодах и в коде, собирает и запускает её и автоматически доказывает, что поведение сохранилось.

### Обязательный путь (слайд 3)

Загрузить .java/.zip → разобрать → построить граф → исследовать и править → собрать Java → запустить и сравнить.
Изменения синхронизируются в обе стороны (код ↔ ноды).

### Ключевой контракт

После любых преобразований тесты подтверждают, что поведение сохранено.

## 2. Стек

- **Бэкенд:** Java 21, Gradle (Kotlin DSL), многомодульный монолит: `model`, `source`, `blocks`, `analysis`, `runner`, `testing`, `fixes`, `benchmark`, `app`. Spring Boot только в `app`. JavaParser + Symbol Solver, `javax.tools.JavaCompiler`. Граф зависимостей модулей — `backend/CLAUDE.md`.
- **Фронтенд:** React + TypeScript (Vite), React Flow (xyflow) + ELK.js для раскладки, Monaco Editor.
- **Запуск пользовательского кода:** одноразовые Docker-контейнеры.
- **Деплой:** docker-compose на VPS; запасной вариант — воспроизводимая сборка `docker compose up`.
- **Хранилище:** без БД и авторизации, проект в памяти по id сессии.
- **LLM:** опционально, только как дополнительный провайдер (см. §9).
- **Сборка:** Gradle wrapper, версии в `gradle/libs.versions.toml`, общие настройки в convention-плагине `build-logic/`. Фронтенд — Vite.
- **CI:** GitHub Actions — сборка + round-trip тесты на корпусе.

### Точки расширения (закладываются сразу, даже с одной реализацией)

| Интерфейс | Сейчас | Позже |
|---|---|---|
| `Detector` | 4+ правила анализа | новые правила без правки остального кода |
| `FixProvider` | детерминированные quick-fix'ы | LLM-провайдер |
| `Refactoring` (`canApply` / `apply`) | quick-fix'ы реализуют его | выделить метод, переместить в класс, переименовать, декомпозиция |

| `Benchmark` | заглушка за кнопкой | эмпирический замер сложности |

## 4. Модель данных

### Блок (нода)

```json
{
  "id": "Main.processOrders/body/2",
  "kind": "foreach",
  "fields": { "type": "Order", "var": "order", "iterable": "orders" },
  "slots": { "body": [ ... ] },
  "span": { "file": "Main.java", "startLine": 31, "endLine": 38 },
  "issues": ["ISSUE-7"],
  "collapsed": false
}
```

`kind`: `method | var | assign | expr | if | while | dowhile | for | foreach | switch | case | try | catch | return | throw | break | continue | comment | raw`.

Правила:
- Метод — это **дерево** вложенных блоков, а не произвольный граф. Стрелки выводятся из дерева.
- **Выражения хранятся текстом** внутри блока, не разворачиваются в ноды. Текст в нодах — с подсветкой синтаксиса Java.
- **`raw`** — всё неподдержанное: исходный текст как есть, генерируется обратно без изменений.
- `span` нужен для подсветки строка ↔ нода и привязки проблем.

### Проблема (Issue)

```json
{
  "id": "ISSUE-7",
  "rule": "LinearSearchInLoop",
  "severity": "high | medium | low",
  "confidence": "high | low",
  "span": { ... }, "blockId": "...",
  "message": "...", "recommendation": "...",
  "complexity": { "before": "O(n·m)", "after": "O(n)" },
  "fixes": ["fix-id"]
}
```

`confidence: low` → проблема показывается во вкладке «Предупреждения» с формулировкой «Возможно…» и **без** кнопки автоисправления.

## 5. Java ↔ ноды

- **Источник правды — текст кода.**
- Правка в нодах: фронт шлёт новое дерево метода → бэкенд генерирует тело метода, подменяет его в `CompilationUnit`, печатает файл → повторный парсинг → новое дерево + анализ.
- Правка в коде: debounce 500 мс → парсинг → новое дерево. При синтаксической ошибке граф остаётся прежним, ошибка показывается.
- Неизменённые методы сохраняются байт в байт (`LexicalPreservingPrinter`).
- **Проверка текста в нодах:** каждая правка разбирается `JavaParser.parseExpression` / `parseStatement`. Неверный синтаксис → нода красная, изменение в код не попадает. Ошибки типов ловит компиляция и показывает на ноде по номеру строки.
- **Комментарии — отдельная нода `comment`** (стикер в последовательности). Добавляется из палитры, перемещается, удаляется. Генерируется как `// текст` (многострочный — `/* */`) перед следующим оператором.
  - Комментарий в конце строки (`x++; // счётчик`) становится нодой и при генерации переезжает на отдельную строку под оператором.
  - Комментарии внутри выражений (`foo(/* id */ 1)`) теряются — описано в ограничениях.
  - На схеме переключатель «показывать комментарии».
- Javadoc метода/класса — свойство метода/класса в форме, не нода.

### Регрессионная страховка

Round-trip тест на корпусе: каждый файл → блоки → Java → компилируется и проходит те же IO-тесты. Корпус: свой монолит + по маленькому файлу на каждую конструкцию из слайда 7. Запускается перед каждым коммитом агента и в CI.

## 6. Редактор нод (вариант B+C)

- React Flow, структурная блок-схема, визуальный стиль Unreal Blueprints: тёмный фон с сеткой, цветные заголовки нод, exec-провода с треугольными пинами.
- Циклы, `if`, `try`, `switch` — контейнеры (parent nodes); раскладка ELK.js.
- **Пользователь не рисует стрелки.** Вставка блока: кнопка «+» на стрелке или перетаскивание из палитры на стрелку. В ноде: правка текста, удаление, перемещение вверх/вниз.
- Палитра: Переменная, Условие, Цикл, Вызов метода, Операция, Возврат, Комментарий, try/catch, throw, switch.
- Большие методы: контейнеры сворачиваются кликом; при вложенности > 3 открываются свёрнутыми. Клик по проблеме разворачивает ветку и центрирует схему. Клик по строке в Monaco подсвечивает ноду. Мини-карта.
- **Страховка к 24-му часу:** если редактирование нод не работает, схема остаётся только для просмотра, правки — в Monaco.

## 8. Анализатор

### 8.1 Оценка Big O

- Сложность — произведение символов размера с log-множителем, например O(n·m), O(n log n).
- Последовательность → максимум; цикл → размер × тело; вызов метода проекта → его сложность (граф вызовов, мемоизация); рекурсия → «рекурсия, оценка неточная» (`confidence: low`).
- Размер цикла: for-each по коллекции/массиву, `i < x.size()`, `i < arr.length`, граница-параметр → символ коллекции; константная граница → O(1); `while` → символ с `confidence: low`.
- Таблица стоимостей JDK (требует резолва типов): `ArrayList.contains/indexOf/remove(Object)` O(n), `LinkedList.get(i)` O(n), `HashMap/HashSet` O(1), `TreeMap/TreeSet` O(log n), `sort` O(n log n), конкатенация строк O(len).
- В бейдже метода показывается упрощённая форма.

### 8.2 Символы размера коллекций

Анализ внутри метода + передача символов через параметры при вызове. Поля классов — **позже**.

- `b = a`, `new ArrayList<>(a)`, `List.copyOf(a)`, `a.clone()`, `Arrays.copyOf(a, a.length)` → тот же символ.
- `a.stream().filter/map(...).toList()`, `a.subList(...)` → тот же символ (верхняя граница).
- Пустая `b` + `add` в цикле по `a` → символ `a`.
- `b.addAll(c)` → n + m (в Big O — max).
- Параметр получает символ аргумента: `merge(orders, orders)` → внутри оба n, вложенный цикл = O(n²).
- Нераспознанное → новый символ, проблема уходит в «Предупреждения».

### 8.3 Детекторы (MVP)

| Правило | Что ищем | Рекомендация |
|---|---|---|
| NestedLoopSameCollection | вложенные циклы по одному символу | индекс по ключу (`LinkedHashMap`) |
| LinearSearchInLoop | `contains/indexOf/remove(obj)` у списка в цикле | `LinkedHashSet` |
| ExpensiveCallInLoop («N+1») | вызов со стоимостью ≥ O(n) в цикле | вынести до цикла / кешировать |
| StringConcatInLoop | `s += ...` в цикле | `StringBuilder` |
| LongMethod / DeepNesting | метрики | выделить метод |

**Позже:** LoopInvariantCall, LinkedListGetInLoop, RemoveFirstInLoop, SortInLoop, дублирование (хеш нормализованных поддеревьев), пустой catch.

### 8.4 Отображение

- Вкладки панели анализа: Проблемы / Предупреждения («Возможно…») / Метрики.
- **Асимптотическая оценка**, не коэффициент ускорения: порядок числа операций при n, заданном пользователем (по умолчанию 10 000), например «≈10⁸ → ≈10⁴ операций», с подписью «асимптотическая оценка».
- «Ускорение в X раз» — только после **замера по кнопке** (`Benchmark`, тяжёлая операция, позже).

## 9. Исправления

- LLM **необязателен**. Без `LLM_API_KEY` продукт работает полностью; кнопки «Предложить через ИИ» нет.
- `RuleBasedFixProvider` (MVP): StringBuilder, `contains` → `LinkedHashSet` (если список не меняется в цикле), индекс по id для вложенного цикла (узкий шаблон, как на слайде 5).
- **Позже:** `LinkedList.get(i)` → for-each, `remove(0)` → `ArrayDeque`, вынос инварианта (только для «чистых» методов), `LlmFixProvider`.
- **Обязательное правило для всех фиксов, включая LLM:** сохранять порядок перебора — `LinkedHashMap`/`LinkedHashSet` вместо `HashMap`/`HashSet`.
- Любой патч проходит Quality Gate: компиляция + все тесты. Не прошло — откат и «исправление не подтверждено».

## 10. Тесты и проверка поведения

### 10.1 IO-тесты (`IoTestSource`)

Файлы `tests/<имя>.json`:

```json
{
  "name": "empty-orders",
  "stdin": "0\n",
  "mode": "original",
  "expected": null,
  "ignoreLines": []
}
```

- `mode: original` (по умолчанию) — эталон получается запуском исходной программы.
- `mode: manual` — ожидаемый вывод задан пользователем. Если тест не проходит **на оригинале**, показывается отдельно: «оригинал тоже не проходит этот тест».
- `ignoreLines` — строки, помеченные пользователем как «игнорировать».
- Импорт при загрузке: папка `tests/` и пары `*.in`/`*.out` подхватываются автоматически. Экспорт проекта включает тесты.
- Редактируются во вкладке «Тесты».

### 10.2 JUnit-тесты (`JUnitTestSource`) — в MVP

- JUnit 5. Тесты в `tests/*.java`, редактируются во вкладке «Тесты» в Monaco.
- Запуск через `junit-platform-console-standalone.jar`, результат читается из XML-отчёта и приводится к общему формату результатов.
- Только при сборке тестов (пользователь не видит): `private` → package-private; тесты компилируются в том же пакете, что и тестируемый класс.
- Режима «как у оригинала» нет: ожидания задают ассерты.
- Статусы: «пройден», «не пройден», **«не компилируется»** (отдельно — значит сломалась структура, а не поведение).

### 10.3 Правило сравнения

- stdout побайтово + exit code + тип и сообщение исключения. Строки stack trace (`at ...`) **не** сравниваются.
- «Поведение совпадает» = все тесты всех источников зелёные.
- Результаты всех `TestSource` в одном формате: имя, тип, прошёл/нет, время, текст ошибки.

### 10.4 Недетерминизм

- Только для запуска (пользователь не видит): `new Random()` → `new Random(42)`, `Math.random()` → общий `Random` с seed.
- Исходная программа запускается **дважды**; различающиеся строки — «шумные», не учитываются, показываются серым.
- Если шумных строк больше половины → предупреждение «программа недетерминирована, проверка неполная», не зелёный статус.

### 10.5 stdin

Если программа читает `System.in`, а тестов нет — зелёный статус заблокирован, показывается «добавьте тест со входными данными» и кнопка создания заготовки.

## 11. Загрузка проекта

### Форматы

- `.java` (один или несколько файлов), `.zip`, `.jar` — **если внутри есть `.java`** (например, `*-sources.jar`). Архивы разбираются одним кодом.
- Загрузка папки целиком (`<input webkitdirectory>`) — на бэк уходит тот же набор файлов.
- Из архива берутся только `.java` и папка `tests/`; `.class`, `pom.xml`, `build.gradle` и прочее игнорируются.
- `.jar` только с `.class` → отказ: «нужны исходники, а не скомпилированный код».
- **Позже:** кнопка «Декомпилировать (с потерями)» через Vineflower.

### Безопасность распаковки

- Отказ на путях с `..` и абсолютных путях (zip slip).
- Лимиты: суммарный распакованный размер 20 МБ, не больше 2000 файлов (zip bomb). Проверка по мере распаковки, а не по заголовкам архива.

### Структура

- Относительные пути `.java` сохраняются как в архиве. Если все файлы внутри одной общей верхней папки — она отрезается (обёртка).
- Source root определяется по объявлению `package` в каждом файле: путь файла минус папки пакета. Поддерживается любая раскладка: Maven/Gradle, `src/`, файлы в корне, пакет по умолчанию.
- У файла в модели два поля: `path` (как в архиве — для экспорта) и `package` (для дерева в UI).
- Дерево проекта в UI строится по пакетам.
- Пакет не совпадает с папкой → предупреждение, загрузка продолжается (компилируем, передавая все файлы явно).
- Два класса с одинаковым полным именем → отказ с перечнем конфликтующих файлов.
- `tests/` ищется в корне архива после отрезания обёртки.
- Экспорт `.zip` возвращает ту же структуру папок, что пришла. Галочка «включить настройки Java Blueprints (`.blueprints/`, `tests/`)», по умолчанию включена.
- Экспорт исполняемого `.jar` (шаг «Собрать Java» со слайда 3):
  - компилируется из **чистого** кода пользователя — без seed, без private→package-private, без инструментации;
  - `Main-Class` в манифесте — выбранная точка входа (та же, что для запуска);
  - внутри только классы, без `tests/` и `.blueprints/`;
  - целевая версия Java 21, рядом с кнопкой — «требует Java 21+»;
  - проект не компилируется → кнопка неактивна и показывает причину;
  - тест: `.jar` демо-монолита через `java -jar` на IO-тестах даёт тот же результат, что обычный запуск.

## 12. API (черновик)

```
POST /projects                 загрузка .zip/.java
GET  /projects/{id}/tree       дерево проекта
GET  /methods/{id}/blocks      дерево блоков метода
PUT  /methods/{id}/blocks      новые блоки → код + анализ
PUT  /files/{path}             новый текст файла → блоки + анализ
GET  /analysis                 проблемы, предупреждения, метрики
POST /issues/{id}/fix          применить фикс → Quality Gate
GET/PUT/DELETE /tests/{name}   управление тестами
POST /run                      запуск
POST /verify                   прогон всех тестов
```

### Синхронизация

- Фронт всегда отправляет **полное** дерево изменённого метода (или полный текст файла), не диффы.
- У проекта счётчик версии: каждый изменяющий ответ его увеличивает и возвращает. Запрос со старой версией отклоняется (409), фронт перезагружает состояние.
- Один пользователь на проект, без WebSocket и совместного редактирования.

## 13. Демо

Основной сценарий — на **своём** монолите с заложенными дефектами (вложенный цикл по id, `contains` в цикле, конкатенация строк, длинный метод). Монолит организаторов — доказательство работы на чужом коде.
Свой монолит генерируется в первые 2 часа и становится регрессионным тестом.

### Сценарий

1. Загружаем свой монолит: дерево проекта и схема метода.
2. В панели — проблема O(n·n) в `merge`; клик → схема центрируется на вложенном цикле.
3. Quick-fix «индекс по id»: код и схема обновились, оценка «≈10⁸ → ≈10⁴ операций».
4. Прогон тестов: IO и JUnit зелёные, «поведение совпадает».
5. Вручную меняем условие в ноде → IO-тест «как у оригинала» краснеет, показываем diff вывода (доказательство, что проверка реальная). Возвращаем.
6. Загружаем монолит организаторов, показываем найденные проблемы.

## 14а. Функции «если успеем» — спецификация

**1. UML-диаграмма проекта.** Классы, интерфейсы, enum/record с полями и методами. Связи: наследование, реализация, ассоциация (поле типа другого класса проекта), зависимость (использование в методе) — определяются точно. Агрегация/композиция — **эвристика** (коллекция или объект из параметра конструктора → агрегация; создан через `new` внутри класса → композиция), помечается в UI как «эвристика». Связи рисуются **только между классами проекта**. Поля-коллекции (`List<T>`, `Set<T>`, `Map<K,V>` — по значению, массивы) дают связь к `T` с кратностью `*`. Типы JDK — только как типы полей внутри карточки класса, без стрелок. Отрисовка в React Flow + ELK в стиле приложения, клик по классу — переход в дерево проекта. Модуль `analysis`.

**2. PMD.** Подключается библиотекой в `analysis`, адаптер `PmdDetector implements Detector`. Находки → вкладка «Предупреждения» с пометкой источника «PMD». Находки привязываются к нодам по номеру строки. Конфиг — `.blueprints/pmd-ruleset.xml` в проекте; в стандартном наборе **выключены правила, пересекающиеся с нашими детекторами** (неиспользуемые члены, конкатенация строк, пустой catch, длинные методы и т.п.), чтобы не было дублей; если пользователь включит их сам — дубли допустимы. Конфиг редактируется в UI (Monaco, XML), экспортируется с проектом. SonarQube — в `docs/IDEAS.md` как опциональный профиль docker-compose.

**3. Мёртвый код.** Уверенное срабатывание — только приватные методы/поля/классы без использования, неиспользуемые локальные переменные, недостижимый код после `return`/`throw`/`break`. Публичный метод без вызовов — «Предупреждения», «возможно не используется». **Считаются использованными:** `main`; любые переопределения (`@Override` или совпадение сигнатуры с методом родителя/интерфейса); `toString`, `equals`, `hashCode`, `compareTo`; всё, что вызывается из `tests/*.java`.

**4. Граф зависимостей классов с циклами.** Граф «класс → классы, которые он использует». Циклы — поиск сильно связных компонент (Tarjan); каждый цикл — Issue «циклическая зависимость» и красная подсветка рёбер на графе. Связи «внешний ↔ вложенный класс» не учитываются. Цикл из 2 классов — серьёзность «низкая», из 3+ — «средняя». Фикса нет, только рекомендация. Отдельная вкладка рядом с UML.

**5. Сложность по памяти.** Вторая оценка рядом с временной: дополнительная память по символам размера (новая коллекция из `a` → O(n), копия → O(n), глубина рекурсии). Часто `confidence: low`. В карточке фикса: «время O(n²) → O(n), память O(1) → O(n)».

**6. Инструментация и покрытие нод.** Только в копии для запуска, как seed для `Random`.
- Каждой ноде — числовой индекс; `Trace.hit(17)` = `counts[17]++` в `long[]`, без строк и мап (иначе O(n²)-программа замедляется в разы).
- Класс счётчика в пакете `__blueprints`, чтобы не совпасть с классами пользователя.
- В конструкторе счётчик ставится **после** `super(...)`/`this(...)`; однострочные `case ->` оборачиваются в блок.
- Результаты пишутся в файл из shutdown-hook (срабатывает при `System.exit` и необработанном исключении). Убита по таймауту → покрытие теста помечается «неполное».
- Таймаут инструментированного запуска — ×3 от обычного.
- **Проверка поведения всегда идёт на чистом коде.** Покрытие — отдельный прогон по кнопке «Посчитать покрытие» и при формировании отчёта.
- Корпус `samples/roundtrip/` — он же корпус для инструментации: каждый файл после инструментации обязан компилироваться; на каждое правило выше — тест.
- UI: непокрытые ни одним тестом ноды серые, у покрытых — число выполнений; процент покрытия нод — в панели тестов. Модули: `runner` (инструментация), `testing` (агрегация).

**7. Экспорт диаграмм.** Схема метода, UML, граф зависимостей — в PNG и SVG кнопкой на холсте.

**8. Шаблоны блоков.** Встроенные шаблоны в палитре: «цикл с индексом», «try-with-resources», «проверка на null с ранним возвратом», «чтение N чисел через Scanner» и т.п. — вставляются готовым поддеревом с подсвеченными полями для заполнения. Поля-заполнители подсвечены, ввод в них обязателен. Имя переменной из шаблона, уже занятое в области видимости, при вставке получает суффикс (`i` → `i2`). Пользователь может выделить ноды и «Сохранить как шаблон». Пользовательские шаблоны хранятся в проекте (`.blueprints/templates/*.json`) и экспортируются вместе с ним.

**9. Встроенная консоль.** Терминал (xterm.js): запуск программы с интерактивным вводом stdin и потоковым выводом. Исключение из правила «без WebSocket» (§12): WebSocket используется **только** для консоли. Кнопка «Сохранить сессию как IO-тест» — введённое становится `stdin`, вывод — ожиданием `manual` или режимом `original`. Песочница та же (§11а), таймаут — на бездействие, а не на всё время. Консоль запускает тот же переписанный код, что и тесты (seed), иначе сохранённая сессия будет недетерминированной. Одна консоль на сессию: новая закрывает старую вместе с контейнером.

**10. Опциональный ИИ-слой.** Модуль `ai`, включается только при `LLM_API_KEY`. `GET /capabilities` сообщает фронту, доступен ли ИИ; без него кнопок нет. Функции: «объясни метод», «предложи фикс» (`LlmFixProvider` → тот же Quality Gate), правка ноды текстом («добавь проверку на null»). Все LLM-фиксы обязаны соблюдать правило порядка перебора (§9). Правка ноды текстом **не применяется сразу**: сначала дифф кода, применение по кнопке (функция намеренно меняет поведение, Quality Gate тут не защищает). Ограничения на сервере: N запросов в минуту на сессию и общий дневной лимит; при превышении — понятное сообщение.

**11. CLI.** Модуль `cli` (picocli) на тех же модулях без Spring: `blueprints analyze <проект> [--fail-on "O(n^2)"] [--format json|text]`, `blueprints verify <проект>` (прогон тестов). Ненулевой код выхода при нарушении — для CI.

**12. Автодополнение.** Бэк отдаёт таблицу символов для позиции (классы проекта, поля, методы с сигнатурами, локальные переменные в области видимости, базовые классы JDK из scope слайда 7). Фронт получает таблицу **для метода целиком** при открытии метода и после каждой его новой версии; область видимости для каждой ноды бэк считает заранее и отдаёт в той же таблице. Фильтрация по введённому тексту — локально на фронте. Без языкового сервера.

**13. Debug-запуск.** Расширение инструментации п.6: кроме `hit` записываются значения локальных переменных после каждого присваивания (`Trace.value`), с ограничением объёма. UI: пошаговое воспроизведение по нодам — текущая нода подсвечена, панель переменных, вперёд/назад, ползунок шагов. Только запись и воспроизведение, без остановки живой программы. Запуск на **одном выбранном тесте**, записываются первые 10 000 шагов (дальше — «запись остановлена, лимит»). Значения: примитивы и строки (обрезанные до 200 символов) — как есть; коллекции и массивы — тип и размер; прочие объекты — тип и идентификатор, **без вызова `toString()`** (он может быть медленным, бросить исключение или изменить состояние). Подсказка: «для отладки выберите тест с маленьким входом».

**14. Командная палитра.** Окно поиска по Ctrl+K (и Ctrl+Shift+P): классы, методы, поля, ноды текущего метода, проблемы и команды («Применить фикс», «Запустить тесты», «Экспорт», «Открыть UML» и т.п.). Нечёткий поиск, Enter — переход или выполнение. Только фронт: данные — дерево проекта, блоки и анализ, которые уже загружены; команды регистрируются списком (`commands.ts`), как вкладки панелей. Библиотека — `cmdk`.

**15. Отчёт об оптимизации.** Экспорт HTML (и PDF через печать браузера): найденные проблемы, применённые фиксы, сложность до/после (время и память), результаты тестов, покрытие, метрики. Модуль `report`.

## 15. Командная работа

Правила для агентов — `CLAUDE.md`, `backend/CLAUDE.md`, `frontend/CLAUDE.md`, `.claude/agents/`.

- **Зоны:** Иван — `backend/`, `samples/`; напарник — `frontend/`, `docker-compose.yml`. Общая зона — только `contract/`, меняется по решению обоих людей отдельным маленьким изменением.
- **Contract-first:** `contract/openapi.yaml` + `contract/fixtures/` пишутся в первый час (CT-01). Фронт генерирует типы и работает на MSW-моках до готовности бэка.
- **Оркестрация:** у каждого одна сессия Claude Code — оркестратор своей зоны. Код пишут субагенты:
  - `be-implementer`, `fe-implementer` — в отдельных git worktree;
  - `verifier` (только чтение + Bash, haiku) — полный прогон проверок, возвращает только упавшее;
  - `reviewer` (только чтение) — проверка диффа на правила;
  - `fixture-builder` (haiku) — фикстуры из `samples/`, только по команде человека.
- **Параллельность:** не больше 3 исполнителей одновременно, только на задачах с разными пакетами; зависимая задача — после влития предыдущей в `main`. При упоре в лимиты — снизить до 2.
- **Отчёт субагента:** шаблон до 15 строк, без кода и логов.
- **Мерж:** оркестратор после зелёного `verifier` и чистого `reviewer` делает squash-merge в локальный `main`. `git push` — только человек.
- **Контракт:** субагент контракт не меняет — возвращает «заблокировано» с предложением.
- **Атрибуция:** в коммитах нет `Co-Authored-By`, `Claude-Session`, `Generated with` — настройка `attribution` в `.claude/settings.json`, правило в `CLAUDE.md`, проверка в `verifier`; оркестратор сам пишет сообщение при squash-merge.
- **Документация и контекст:** `docs/STATUS.md` — «сохранение игры», обновляется после ~5 задач, затем `/clear`. `docs/decisions.md` — журнал решений. README в каждом пакете/фиче заменяет агенту чтение исходников.
- **Задачи:** `docs/TASKS.md`, у каждой — что трогает и от чего зависит.
