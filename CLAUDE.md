# Java Blueprints — правила для агентов

Веб-инструмент: Java-проект ↔ граф нод, анализ сложности и дефектов, правка, сборка, проверка поведения тестами.
Хакатон 48 ч, 2 человека. Полное ТЗ: `docs/TZ.md` — **читай только нужный раздел**, не весь файл.

## Что читать в начале любой работы

1. `docs/STATUS.md` — что готово, что в работе, что сломано.
2. `docs/TASKS.md` — только свою задачу.
3. `README.md` модуля, с которым работаешь. Исходники модуля открывай, только если README не хватает.

Не читай весь репозиторий «для понимания». Для поиска по коду используй субагента Explore.

## Структура и владельцы

| Папка | Владелец | Кто может менять |
|---|---|---|
| `backend/` | Иван | только бэкенд-оркестратор и `be-implementer` |
| `frontend/`, `docker-compose.yml` | напарник | только фронт-оркестратор и `fe-implementer` |
| `contract/` | общая | **только по явной команде человека** |
| `samples/` | Иван | бэкенд-сторона |
| `docs/` | общая | см. правила документации ниже |

Менять чужую папку запрещено, даже если «там очевидный баг» — опиши его в отчёте.

## Контракт — главное правило

`contract/openapi.yaml` и `contract/fixtures/` — единственный источник формата данных между фронтом и бэком.
- Не меняй контракт сам. Если задачу без этого не сделать — верни статус «заблокировано» и предложение изменения.
- TS-типы фронта генерируются из контракта, руками не пишутся.
- Java-DTO бэка пишутся руками и проверяются тестом на соответствие схеме.

## Инварианты продукта (нарушать нельзя)

- Метод — **дерево** блоков, не произвольный граф. Выражения — текст внутри блока.
- Неподдержанная конструкция → блок `raw` с исходным текстом. Код никогда не теряется.
- Источник правды — текст кода. Неизменённые методы сохраняются байт в байт.
- Автоисправления сохраняют порядок перебора: `LinkedHashMap`/`LinkedHashSet`, не `HashMap`/`HashSet`.
- LLM в продукте необязателен: без `LLM_API_KEY` всё работает.
- Новое правило анализа / фикс / источник тестов / рефакторинг — **новый класс**, зарегистрированный в списке. Не `if` в существующем классе.
- Любой `Refactoring` обновляет ссылки во всех файлах проекта, включая `tests/*.java`.

## Definition of Done (перед каждым коммитом)

- Бэк: `cd backend && ./gradlew build` (все модули, включая round-trip на корпусе `samples/`).
- Бэк: новая зависимость между Gradle-модулями — только по таблице в `backend/CLAUDE.md`.
- Фронт: `cd frontend && npm run typecheck && npm run lint && npm test`.
- Изменился публичный интерфейс модуля → обнови его `README.md`.
- Без зелёных проверок коммит не делается, даже если «осталась мелочь».
- Тест не правится ради того, чтобы он прошёл. Падает тест — чини код или верни «заблокировано».

## Git

- Сообщение коммита: `<ID задачи>: <что сделано по-русски>`, например `BE-07: детектор конкатенации строк в цикле`.
- **Никаких трейлеров атрибуции**: без `Co-Authored-By`, без `Generated with Claude Code`, без `Claude-Session`. Автор коммита — человек. Это же проверяет `verifier` перед каждым мержем.
- `git push` запрещён агентам. Пушит человек.
- Никаких `git push --force`, `git reset --hard` по `main`, переписывания истории `main`.

## Документация

- `docs/TZ.md` — меняется только по решению людей.
- `docs/decisions.md` — журнал решений, по 2–3 строки: что и почему. Дописывает оркестратор, когда человек принял решение.
- `docs/architecture.md` — модули и интерфейсы, коротко.
- `docs/STATUS.md` — состояние. Пишет только оркестратор.
- `docs/TASKS.md` — задачи. Каждая сторона правит только свой раздел.
- `README.md` в каждом пакете/фиче — 10–20 строк: что здесь, главный класс/компонент, как тестировать.

## Роль: оркестратор (основная сессия человека)

Этот раздел относится **только к основной сессии**. Субагенты следуют своему системному промпту.

Ты не пишешь код сам. Ты:
1. Читаешь `STATUS.md` и свой раздел `TASKS.md`.
2. Выбираешь задачи, у которых выполнены зависимости. Параллельно — не больше **3** исполнителей и только на задачах с **разными** Gradle-модулями / фичами фронта (колонка «Трогает» в `TASKS.md`).
3. Раздаёшь задачи субагенту-исполнителю своей зоны (`be-implementer` / `fe-implementer`): ID задачи, ссылка на раздел ТЗ, затрагиваемые пакеты, что уже готово из зависимостей.
4. По отчёту исполнителя: зовёшь `verifier`, затем `reviewer` на его ветку.
5. Оба зелёные → `git merge --squash <ветка>` в **локальный** `main`, коммит `<ID>: ...`, удаляешь worktree и ветку.
6. Красное → возвращаешь задачу тому же исполнителю (resume) с кратким списком замечаний. Две неудачи подряд — останавливаешься и спрашиваешь человека.
7. Статус «заблокировано» из-за контракта → показываешь человеку предложение изменения и ждёшь решения.
8. Отмечаешь задачу в `TASKS.md`, строку в `STATUS.md`.
9. После каждых ~5 закрытых задач или крупного этапа: полностью обновляешь `STATUS.md` (готово / в работе / висящие ветки / заблокировано / следующие шаги) и пишешь человеку «можно /clear». После `/clear` начинаешь с `STATUS.md`.
10. Даёшь человеку сводку для пуша: какие задачи влиты, что проверено.

Никогда не вставляй в свой контекст листинги кода и логи субагентов — только их отчёты.
